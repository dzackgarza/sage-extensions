## The observed API boundary

`isotropic_induction.py:304`:

```python
return tuple(lattice.integral_isometry(generator)
             for generator in action.stabilizer().group_generators())
```

The call returns **owned integral isometries**, each already constructed (with the
certified inverse that `integral_restriction`'s fast path builds per element).  A caller
of `automorphism_group_generators` therefore cannot reach the raw stabilizer family or
its finite images through this API; that is the obligation.

The consumer in this repository reads `rho(s)` per generator only.  For an integral
isometry `s`, `rho(s)` is the forward class action `[z] |-> [s.z]` on `L*/L`, which does
not require an inverse of `s`.  So the *API shape* is not matched to that consumer.

## What is not claimed

- That the current path is the cause of the pending run's duration.
- That no in-repo owner improvement is possible.  The port's return type prevents a
  *downstream* caller from bypassing the conversion in that call; it does not establish
  that this repository could not improve its own owners -- for instance by making the
  per-generator construction cheaper, by caching, or by another stabilizer-producing
  route whose image is proved equal.  Any such change is a separate question requiring
  its own evidence and its own regression.
- That any test is red.  The Enriques module's orbit assertions are **unrun**: they have
  never executed, so there is no observed failure and no reproduced failing regression.

## What an owning-side change would have to preserve

If the port exposes either the raw stabilizer family or its `O(A_L)` image, the consumer
here keeps exact image equality: its subgroup is generated by `rho` of the same family,
with no overgroup, no arbitrary lifts and no cardinality proxy.  Whether to make that
change is the owning repository's decision; this repository is not modified for it.
